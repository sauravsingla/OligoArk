# Scalable archival storage

OligoArk now has two archive surfaces with deliberately different goals:

- the existing `oligoark-archive-v1` JSON format remains the human-readable research format;
- `oligoark-stream-v2` is a length-prefixed, 2-bit-packed binary container designed for
  bounded-memory file archival and scale experiments.

The binary container reuses the existing OligoArk v1 strand frame, so frame semantics,
logical indexes, CRC, optional Reed-Solomon protection, XOR/fountain redundancy, and the
final SHA-256 integrity gate remain compatible with the research codec. The scalable path
does not retain every DNA string in memory. Data chunks are encoded sequentially, XOR
parity is emitted per group, fountain symbols are generated by bounded random-access reads,
and recovery writes decoded chunks directly to their logical offsets in the output file.
XOR parity is consumed immediately during recovery instead of being retained for the whole
archive.

## CLI

For a software-scale archive:

```bash
oligoark archive-stream input.bin --output input.oligoark.bin --profile scale-1024
oligoark recover-stream input.oligoark.bin --output recovered.bin
cmp input.bin recovered.bin
```

The `scale-1024` profile is intentionally a **software scaling profile**. It uses a
1024-nt maximum frame, no inner Reed-Solomon parity, and XOR redundancy by default so the
100 MiB acceptance run primarily measures streaming, packing, erasure recovery, throughput,
and memory behavior rather than the speed of the pure-Python RS implementation.

For physical-design experiments use one of:

| Profile | Target full-strand length | Inner RS |
| --- | ---: | ---: |
| `oligoark-152` | 152 nt | 8 symbols |
| `oligoark-200` | 200 nt | 8 symbols |
| `oligoark-248` | 248 nt | 8 symbols |

These are **software sequence profiles**, not synthesis validation.

## Scale benchmark

Run the pull-request/CI-sized profile:

```bash
python benchmarks/run_storage_scale.py --profile ci
```

Run only the mandatory scale gate:

```bash
python benchmarks/run_storage_scale.py --profile acceptance
```

Run the complete research matrix:

```bash
python benchmarks/run_storage_scale.py --profile full
```

The full matrix covers 1 KiB, 64 KiB, 1 MiB, 10 MiB, and 100 MiB payloads; none/XOR/fountain/
hybrid redundancy; and clean, 1% controlled dropout, 5% controlled dropout, substitution,
indel, and mixed software faults. Each case runs in an isolated process and reports exact
SHA-256 recovery, logical bits/nt, total encoded nt, strand count, redundancy, compact
archive overhead, encoding/recovery throughput, wall time, peak RSS, and sampled GC/
homopolymer pass rate.

The payload is deterministic but heterogeneous: UTF-8 text, JSONL records, Python source,
PPM image bytes, random binary, compressed binary, and a ZIP mixed-file archive are combined
and repeated to the requested exact byte size.

## Mandatory 100 MiB gate

The acceptance profile runs a 100 MiB (104,857,600-byte) heterogeneous payload with XOR
redundancy in two conditions:

1. clean recovery;
2. controlled 5% data-strand erasure, constrained to at most one erasure per XOR group.

The benchmark writes the milestone sentence only when **both** runs reproduce the source
SHA-256 exactly:

> OligoArk successfully archives and SHA-256 recovers a 100 MB heterogeneous dataset under
> clean and controlled-loss conditions, with measured density, throughput, peak memory and
> redundancy overhead.

If either run fails, `summary.json` records the exact failure instead. The scheduled
`Storage scale acceptance` GitHub Actions workflow treats failure to achieve the milestone
as a failing job.

## Claim boundary

The scale benchmark is software evidence. Controlled erasures are not measured synthesis or
sequencing dropout. The external CNR, Grass, LCRC, and DNAformer Pilot workflows are a
separate evidence class based on published physical reads. A future wet-lab OligoArk claim
requires synthesizing OligoArk-generated strands, sequencing them, recovering the archive,
and passing the original-file SHA-256 gate.
